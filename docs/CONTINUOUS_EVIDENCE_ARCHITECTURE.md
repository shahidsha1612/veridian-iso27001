# Continuous Evidence Architecture

## The problem this exists to solve

The standard compliance-automation pattern (Vanta/Drata/Secureframe-style,
and most manual audit prep) works like this: an integration polls an API
*at whatever moment the tool happens to check*, or a human takes a
screenshot, and that becomes "the evidence" for a control until someone
looks again. Two failures follow directly from that:

1. **Evidence goes stale silently.** A screenshot of "MFA enforced" taken
   in March says nothing about whether MFA was still enforced in April.
   Someone could disable it five minutes after the screenshot and nothing
   would notice until the next audit cycle, if then.
2. **Evidence isn't tamper-evident.** A screenshot, a CSV export, a PDF: all
   of these can be edited, regenerated, or quietly replaced without leaving
   a trace, and nothing proves *when* it was actually true.

The capstones you built (PayVault/Sentinel/Acme Health) already solve a
version of this with Cosign signing + SHA-256 hashing + S3 Object Lock: an
evidence artifact, once written, cannot be altered or deleted, and its
signature proves it came from the pipeline, not a person's hands. This
document generalizes that pattern from "one CI run's worth of evidence" to
**a control's evidence staying valid across the entire period between
audits**, which is what ISO 27001 (and SOC 2 Type II) actually require:
operating effectiveness *over time*, not a point-in-time snapshot.

## The architecture

```
                     ┌─────────────────────────────────────────┐
                     │              CONTROL SOURCE               │
                     │  (Terraform state, IAM config, CI runs,   │
                     │   HRIS/MDM/LMS APIs, CloudTrail, etc.)    │
                     └───────────────────┬───────────────────────┘
                                         │
                      ┌──────────────────┴──────────────────┐
                      │                                     │
              EVENT-TRIGGERED CHECK                 SCHEDULED RE-CHECK
           (on every PR / deploy / merge)          (cron: hourly/daily/weekly
                      │                              per control's freshness SLA)
                      │                                     │
                      └──────────────────┬──────────────────┘
                                         ▼
                          ┌───────────────────────────┐
                          │   POLICY EVALUATION (OPA)  │
                          │  control-id-tagged Rego    │
                          │  pass/fail against current  │
                          │  live state, not intent     │
                          └─────────────┬─────────────┘
                                         ▼
                          ┌───────────────────────────┐
                          │   EVIDENCE MANIFEST BUILD   │
                          │  {control_id, timestamp,    │
                          │   result, evaluated_state,  │
                          │   evaluator_version,        │
                          │   commit/run_id}            │
                          └─────────────┬─────────────┘
                                         ▼
                          ┌───────────────────────────┐
                          │   SHA-256 + COSIGN SIGN     │
                          │  (keyless, GitHub OIDC ->   │
                          │   Sigstore/Rekor, same as   │
                          │   the capstone pattern)     │
                          └─────────────┬─────────────┘
                                         ▼
                          ┌───────────────────────────┐
                          │  EVIDENCE VAULT (S3, Object │
                          │  Lock GOVERNANCE, separate  │
                          │  AWS account from workload) │
                          │  append-only, never edited  │
                          └─────────────┬─────────────┘
                                         ▼
                          ┌───────────────────────────┐
                          │   FRESHNESS + DRIFT ALARM   │
                          │  if a control's last-pass   │
                          │  timestamp exceeds its SLA, │
                          │  or a check *fails*, alert  │
                          │  before an auditor ever asks │
                          └───────────────────────────┘
```

## Core principles

1. **Evidence is generated by re-evaluating live state, not by exporting a
   claim.** A Rego policy queries the actual current Terraform plan/state or
   a live AWS API response, so it cannot be "marked done" by a person;
   either the live system passes the check or it doesn't.
2. **Every control has a freshness SLA, not just a pass/fail.** T1 controls
   (control-as-code) get the tightest SLA, checked on every merge *and* on
   a schedule (e.g., every 6 to 24h) regardless of whether anything changed,
   because infrastructure can drift outside of Terraform (console changes,
   expired policies, manual overrides). T2 controls get an SLA matched to
   how often the underlying system of record plausibly changes (e.g.,
   offboarding-deprovisioning checked daily; training completion checked
   weekly). T3 controls get a calendar review date, tracked explicitly.
3. **A missed check is itself a finding.** If the scheduled re-check job
   fails to run (not just fails its assertions), that's alerted exactly like
   a failed control. Silence is not evidence of compliance.
4. **Nothing in the evidence vault is ever edited or deleted before its
   retention period.** Object Lock in GOVERNANCE mode (matching the Acme
   Health capstone's documented trade-off: tamper-evidence against ordinary
   callers, while a privileged break-glass role can still manage lifecycle
   for cost/legal reasons). A corrected finding produces a *new* evidence
   artifact referencing the old one; history is never rewritten.
5. **The evidence vault lives in a separate AWS account from the workload**,
   with write-only (not delete) access from the workload account's CI role.
   This was an accepted trade-off in the Acme Health capstone ("next sprint"
   item); for Veridian it's a day-one requirement, not deferred, because
   this program is meant to hold up to a real accredited auditor.
6. **Every artifact is independently verifiable by a third party.** An
   auditor (or you) can take any `{control_id, timestamp}` pair, pull the
   signed manifest from the vault, recompute its hash, verify the Cosign
   signature against the public Rekor transparency log, and confirm Object
   Lock retention is still active: exactly what
   `scripts/verify-evidence.sh` does in the capstones, extended here to
   cover the full control catalog instead of one deploy's worth of proof.

## Evidence manifest schema (draft)

```json
{
  "control_id": "8.5",
  "framework": "ISO27001:2022-AnnexA",
  "check_name": "iam-mfa-enforced",
  "evaluated_at": "2026-09-12T04:00:00Z",
  "result": "PASS",
  "evaluated_state_ref": "aws-config-aggregator-snapshot://...",
  "policy_ref": "policies/iam_mfa.rego@<git-sha>",
  "trigger": "scheduled",
  "run_id": "gha-run-123456",
  "freshness_sla_hours": 24,
  "previous_manifest": "s3://veridian-evidence-vault/8.5/2026-09-11T04-00-00Z.json"
}
```

Signed as `<manifest>.json` + `<manifest>.json.sig` (Cosign), uploaded to
`s3://<evidence-vault>/controls/<section>/<control-id>-<control-slug>/<timestamp>.json`
(e.g. `controls/governance/5.1-policies-for-information-security/...`),
Object Lock applied on write. The section matches the #tag grouping in
[`IMPLEMENTATION_CHECKLIST.md`](IMPLEMENTATION_CHECKLIST.md), not Annex A's
own 5/6/7/8 numbering, so evidence can be browsed the same way the program
is built: one section at a time. `scripts/evidence/control_catalog.py` is
the single source of truth for control-id -> section/slug, kept in sync
with the checklist. Clause-level evidence (Clause 4-10, if produced) would
get a parallel `clauses/<clause-id>-<clause-slug>/` prefix instead.

## Mapping to the Statement of Applicability

Every T1 and T2 row in
[`STATEMENT_OF_APPLICABILITY.md`](STATEMENT_OF_APPLICABILITY.md) gets one or
more entries in this pipeline. T3 rows get a lighter version: a dated
document plus a calendar reminder, tracked in `docs/policies/`. The goal
over time is to shrink the T3 column by finding a system-of-record API for
each one (e.g., once an HRIS is chosen, 6.1/6.2/6.5/6.6 move from wherever
they start toward T2).

## What we build first

1. `terraform/` baseline for the prod AWS account (VPC, KMS, evidence-vault
   account bootstrap, CloudTrail, Config, GuardDuty): this is the
   "control source" layer.
2. `policies/`: Rego policies for the T1 cluster identified in the SoA
   build-order note, each tagged with its control ID(s).
3. `.github/workflows/evidence-pipeline.yml`: the event-triggered *and*
   scheduled re-check job that produces signed manifests per the schema
   above.
4. `scripts/verify-evidence.sh`: generalized from the capstone version to
   verify any control's evidence chain, not just one deploy's.
5. `oscal/`: component definition referencing Annex A control IDs, so the
   whole thing is expressible in the same machine-readable format an
   auditor/tool can ingest.
